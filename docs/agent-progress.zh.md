# Agent 进度诊断与有限交接

长时间运行可能意味着需要读原文、推导、调试或等待真实软件，也可能意味着重复润色。单凭耗时无法区分这些情况。Codex 提供者的 `--timeout` 现表示进度检查间隔，不再是中止活动 turn 的硬截止时间。

```bash
research-assistant run ./study --brief "回答一个明确的科研问题" --timeout 600
```

活动 turn 每经过一个间隔，程序通过 SDK 的 `turn.steer()` 提问：当前在做什么、为什么尚未返回、已有最佳候选或产物是什么、相比上次改变了什么、还需要什么证据，以及工作属于必要的慢任务、来源核查还是没有新增证据的重复润色。请求的是简短的公开工作说明与依据，不是模型私有推理过程。

程序只消费一条公开 turn 通知流。诊断报告使用带标记的 commentary JSON；最终返回仍符合原任务输出 schema。reasoning 类通知不进入诊断、判断或日志。如果模型没有给出诊断、无法给出有效结构化报告，或仅表述“还在想”，工作保持活动状态，下个检查点继续提问。沉默与未知状态不会被当成无进展证据。

## 怎样反馈

默认策略对必要慢任务、原文核查和不明确状态继续等待。只有两个不同检查点的公开报告同时描述同一候选的重复润色、没有新证据，并提供具体重复工作引用和变化说明，才请求返回当前最佳候选供外部评阅。它不调用 `interrupt()`，也不将当前候选判为科学支持或最终完成。专家仍需保留未解决验证、负面发现和适用限制。

这些默认依据来自 worker 自报；记录明确标记为尚未独立核实。它们只足以提出可评阅的交接请求，之后仍需协调者检查原始产物、独立评阅与请求者处置。标签 `repeated_polish` 本身、单次超时或累计耗时都不足以触发候选交接。

调用方可以提供 `progress_callback(event)`，同步或异步均可。回调可以保存所有提问、报告和决定。在 `diagnostic_report` 事件上，它也可以返回下列决定：

```python
{"action": "continue", "reason": "仍在核对必要原文", "evidence": []}
```

或在已检查具体工作记录的基础上要求交接：

```python
{"action": "request_best_candidate",
 "reason": "候选已经可供评阅，连续修改未改变证据或论断",
 "evidence": ["results/report.md 的版本 2 与版本 3，仅文字变化"]}
```

没有理由、没有证据的候选交接决定会被拒绝并记录；回调错误不会取消活动 turn。接口不接受基于时间的自动 interrupt。事件包括 `request_id`、`kind`、`thread_id`，以及相应的 `question`、`checkpoint`、`report` 或 `decision`。内存记录位于 `provider.progress_records[request_id]`；应用层可以通过回调将它们持续写入项目执行账本。报告与协调反馈保持可观察，不能仅靠控制台等待或静默修改预算。

本应用的 `run_project` 已接入持久回调：每条公开事件立即存入 `.research-assistant/execution.json` 的 `calls[request_id].progress`，包含真实 thread 身份。已有调用者回调保留，其决定仍可返回；会话结束恢复原回调。并行角色的事件按请求分别归属，失败返回也保留事件。运行中的记录因此可供协调者检查，而不必等最终 JSON 出现。对于只直接调用 `provider.ask()` 的外部程序，持久存储仍由调用方配置。

## 启动、取消与边界

SDK 连接、thread 创建及获取 turn handle 的启动阶段仍有独立的传输超时，默认 60 秒，可以通过 `startup_timeout_seconds` 设置。启动失败会明确报错和关闭客户端；尚未拿到活动 turn handle 时，程序不能保证远端没有发生任何操作，需要按调用账本检查真实状态。

用户或调用者明确取消任务时，程序仍会尽力请求 SDK turn 中断并清理客户端。中断模型 turn 不保证停止已经启动的外部求解器。进度检查间隔达到时则不会取消模型、清理活动客户端或强制终止计算。

`await provider.wait_for_turn(turn, request_id)` 可用于监测已取得的 SDK turn；它不拥有外部客户端的生命周期，调用方应保持连接并最终关闭客户端。显式取消该等待仍请求 turn 中断。

本机制既不读取隐藏思考，也不计量 Codex 内部每条工具调用。它依赖 worker 能够提供公开进度、回调能够检查相关记录，以及下游评阅能处理最佳候选与缺口。检查点提示没有得到响应时会继续等待，因此它不是服务健康检查或总计算资源配额；这些能力需由独立的工具与运行监控实现。
